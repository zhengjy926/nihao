# ECSP 会话由实例自行推进，发送完成决定活跃时间

ECSP 的解帧、握手、心跳、事务序号缓存、上传模式和待发调度属于同一个实例。`app` 静态持有实例，并提供时间、UART 字节和板卡命令；它不查询会话状态来安排握手上报。实例每次推进只消费应用给定的字节预算和至多一帧。中断只追加接收字节或报告 UART 发送结果，命令在主循环执行。

发送 adapter 区分已接受整帧、暂时忙和链路故障。ECSP 保留忙时的待发帧，优先发送事务应答，再发故障等单次事件，最后发送周期握手或心跳。周期上报可合并；队列满或链路故障可观测。心跳静默期从 UART 确认整帧成功发送起算，入队或 DMA 接受不算成功发送。

重新握手清空事务序号缓存，并丢弃尚未交给 UART 的旧业务应答和事件；已经交给 UART 的帧无法撤回。长耗时命令在协议推进中只作有界受理和即时应答，实际执行由应用后续推进，完成时把结果事件交给 ECSP。板卡命令的参数与行为仍在应用，ECSP 负责通用协议规则。

## 考虑过的方案

- 由应用定期调用握手上报并自行查询会话状态：把会话时序散到每个调用者，新增心跳时还要重复修改应用。
- 发送帧入队即更新心跳时钟：UART DMA 忙或链路故障时会虚报活跃，与规范的「成功发出」不符。
- 重新握手后保留旧队列事件：可能把旧会话通知送进新会话；状态仍可由获取类命令查询。
- 直接照搬参考 ECSP 仓库的公开上下文字段和字节 FIFO：本工程已约定由应用持有不透明实例，并使用异步 DMA 的整帧交接。

## 后果

- 主机测试和板上代码通过相同的字节、时间、发送结果和命令调用面验证会话与事务行为，不依赖内部游标。
- 具体接收、发送容量及每轮预算需要按最坏主循环间隔核算；不能因为接口有预算就假定命令回调本身有界。
- 依照 ADR-0015，应用仍决定各模块的推进顺序；ECSP 不接管主循环。
